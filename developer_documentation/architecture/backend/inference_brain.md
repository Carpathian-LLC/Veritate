# inference_brain (PyTorch)

## What it is

The PyTorch inference path used by the Generation tab. Lives under [veritate_mri/inference/](../../../veritate_mri/inference/). Co-exists with the C engine — selectable per request.

## How it works

- [pytorch.py](../../../veritate_mri/inference/backends/pytorch.py) — loads a `.pt` checkpoint, holds the model in memory with a lock for thread safety. Reloaded on model switch or idle-unload.
- Model construction goes through [veritate_core/load.py](../../../veritate_core/load.py)`::load_from_state_dict`, the single sanctioned branch point (preflight 11a). It dispatches on the checkpoint's `training_args.trunk`: `dense` takes the canonical path; `patched`/`hybrid`/`hybrid_moe`/`looped`/`recurrent` build the research trunk classes (`state_rule` threaded, `strict=True` load). The brain therefore serves research-trunk checkpoints (e.g. hybrid chat models) through `/generate` unchanged.
- [decode/](../../../veritate_mri/inference/decode/) — decoding strategies: greedy, nucleus sampling, temperature schedule. Per-token telemetry emission for the dashboard.

### Device (CPU / GPU)

The brain picks its device from `VERITATE_INFER_DEVICE` (`auto` | `cpu` | `cuda` | `mps`) via `_pick_infer_device`; when the env var is unset it falls back to the persisted `device_preference` setting. `auto` prefers CUDA, then MPS, then CPU. `/meta` reports the live device as `pytorch_device` and the dashboard shows it as a `device` chip. Weights run in fp32 on any device, so greedy decodes are byte-identical CPU vs MPS (verified 40/40 on the 200M hybrid); accelerators win because the per-byte forward is FLOP-bound.

**CPU inference thread autotune.** When the forward lands on CPU, batch-1 byte decode is latency-bound: past a few threads the OpenMP pool spin-waits at the per-token barriers (100% CPU, low throughput) instead of computing, but *how many* threads is optimal is machine-specific (a bandwidth-rich core stays flat across counts, an x86 core has a real minimum). So instead of a per-machine constant, the box **measures itself**. Once the device + shape are known, `Brain.__init__` calls `hardware.optimal_infer_threads(device, hidden, ffn, layers, threads)` ([veritate_core/plugin/hardware.py](../../../veritate_core/plugin/hardware.py)) and `torch.set_num_threads` to the result. On CPU `_probe_infer_threads` times a representative batch-1 decode step (the hidden/ffn GEMVs one token runs) at `1, 2, 4, … , cores` threads and returns the **smallest count within `INFER_TIE_MARGIN` (8%) of the fastest** — frugal: a flat curve settles low with no speed loss, a spin-wait curve lands on its true minimum. The probe runs once per `(arch, cores, hidden, ffn)` and is cached (`_INFER_THREADS_CACHE`), so it costs ~1 s on the first load of a shape and nothing after. On MPS/CUDA the forward runs on the accelerator, so the full count (`auto_thread_count`) is kept with no probe. The checkpoint load above still uses the full count. `VERITATE_INFER_THREADS` (int) forces a value (CI / debugging), and `Brain.__init__` logs `inference threads N -> M (cpu, autotuned)` when it changes. This only affects the PyTorch backend; the C engine subprocess sets its own threads.

Measured on an i7-9700T (8 cores, no HT): a 768/3072/12 model decodes at 1322/769/566/536 ms per probe sweep at 1/2/4/8 threads, so the autotune picks **4** (8 is only 5% faster); a 320/1280/8 model decodes at 132/98/81/70 ms, so it picks **8** (4→8 is 15% faster). Same box, shape-dependent — which is why the count is measured, not a constant. A bandwidth-rich core (Apple Silicon CPU) has a near-flat curve and settles at 1.

The split that makes the GPU actually help: the **forward runs on the device**, but **per-token telemetry runs on CPU**. Each MRI frame is hundreds of small ops with `.item()`/`.tolist()` syncs, which stall the GPU far more than they cost on CPU (an all-on-device build measured *slower* than pure CPU: 257 vs 149 ms/byte on the 200M). So captured activations are batch-moved to CPU once after each forward (`_captures_to_cpu`, one sync point, not per-block inside the hooks), and the derived tables (`byte_direction`, `W_E_T`, `emb_w`) plus `last_logits` are kept CPU-side. Net on the 200M: forward 3.5x faster on MPS (40 vs 142 ms/byte), full-MRI stream 2.3x (65 vs 149). `PYTORCH_ENABLE_MPS_FALLBACK=1` is set as a safety net for any op without an MPS kernel; the hybrid recurrent forward uses only MPS-native ops today, so it is not exercised on the hot path.

### Repetition control

[decode/repetition.py](../../../veritate_mri/inference/decode/repetition.py)`::RepetitionController` is the shared byte-level loop guard, applied in both `Brain.stream` and every `stream_fast` submode (through `_sample_one`). Two mechanisms over a sliding window of the last `rep_window` generated bytes:

- **no-repeat-ngram (hard ban).** A candidate byte that would complete an `no_repeat_ngram`-byte sequence already emitted verbatim is masked to `-inf` before top-k. At byte level `n ~ 16` blocks verbatim phrase loops; single-byte penalties are too crude (every byte recurs).
- **suffix-repeat penalty (soft).** A byte that extends the current longest verbatim suffix run (length `>= REP_MIN_MATCH = 4`, below the ngram threshold) is demoted by `rep_penalty * (run - min_match + 1)` nats on the selected top-k logits. Applied post-temperature so the demotion factor `exp(-p)` is scale-free — identical across the PyTorch and C samplers despite their different raw-logit scales.

Defaults (chat): `rep_window=256`, `rep_penalty=0.5`, `no_repeat_ngram=16`. Threaded from `/generate` (`rep_window`/`rep_penalty`/`no_repeat_ngram`), on for chat mode, off (all zero) for autocomplete. With everything off the controller is a no-op and sampling is bitwise-identical to the pre-feature path (parity preserved). The C engine sampler ([model.c](../../../veritate_engine/v1/src/model.c)`::sample_token_ext`) mirrors this algorithm and constants byte-for-byte; keep the two in sync.

### Chat turn-stop

`/generate` wraps BOTH backend streams (the PyTorch `Brain.stream`/`stream_fast` generator and the C `_c_engine_stream`) in the same `_stop_on_bytes(gen, _chat_stop_seq(prompt))` at the route level ([backends_routes.py](../../../veritate_mri/routes/backends_routes.py)), so chat stop behavior is identical across C and PyTorch — a single source of truth, no per-backend divergence. For a framed prompt the wrapper halts at the FIRST turn marker (`<|end|>`, `<|user|>`, `<|assistant|>`; ChatML `<|im_end|>`/`<|im_start|>`) and emits a synthetic `stop` event carrying the marker in `reason`. The multi-marker set matters because the multi-turn SFT model frequently opens a next `<|user|>` turn without first emitting `<|end|>`; watching only `<|end|>` let the whole self-conversation stream. The C `chat_traced` subprocess keeps generating internally after the route stops pulling; `CTracedSubprocess._drain_to_tend` ([c_engine.py](../../../veritate_mri/inference/backends/c_engine.py)) drains the buffered frames + `TEND` (or kills+respawns) so the next request starts on a clean pipe. `/hybrid/chat` reuses the same wrapper in `_generate_local` for an early stop, then `_trim` does the final cleanup.

Serving splits on a per-request trace flag over the one shared subprocess (no second model load): `_c_engine_stream(..., trace=...)` threads `do_trace` into the header and dispatches on the frame marker. Fast is the default (`trace=False`): the engine runs `chat_traced` with tracing off, emits coarse 16-byte `FFRM` frames, and `_c_engine_stream` yields `fast_byte` events that `collect`/`_local_delta_stream`/`_stop_on_bytes` render identically to `token` events. The `/generate` MRI view opts into `trace=True` for the full `TFRM` per-byte telemetry (`_build_c_mri_frame`); so does the chat/OpenAI serving path when a request sets `mri:true` (`_local_events(..., mri=True)` → `_c_engine_stream(..., trace=True)`, see [hybrid_chat.md](hybrid_chat.md)). So the chat no longer pays the logit-lens matvec + DLA-scan cost when nobody is watching the MRI; output bytes are identical to the traced path for the same request, so the `mri` flag never changes generation (see [veritate_engine.md](veritate_engine.md)).
### Fast decode: prompt/n-gram lookahead

`Brain.stream_fast(mode="lookahead")` ([pytorch.py](../../../veritate_mri/inference/backends/pytorch.py)`::_stream_fast_lookahead`) is the PyTorch chat decode path — `hybrid_routes.py::_local_events` selects it for the pytorch backend in place of the full-telemetry `stream()`, except when a request sets `mri:true`, which routes through `_pytorch_mri_events` → `Brain.stream` for the per-byte frames (both share the same sampling defaults, so the flag chooses telemetry, not output). No draft model, no training: `_ngram_draft` matches the last `LOOKAHEAD_NGRAM` bytes of the context against the most recent earlier occurrence (`bytes.rfind`) and takes the up-to-`LOOKAHEAD_DRAFT` bytes that followed as a draft, then verifies the draft byte-exactly in ONE forward over `window ++ draft`. Each position is sampled through the shared `_sample_one`, so **every emitted byte is a fresh draw at its true-prefix logits** — the draft only decides how many positions one forward verifies. A match commits several bytes for a single forward; a miss commits one byte from a slightly-widened forward. No snapshot/restore of rep/constraint state is needed (unlike `mtp-verify`): the draft is a text guess, never an un-sampled emitted byte, so rep/constraint/addons advance in lockstep with the committed bytes.

Windowing mirrors `stream()`'s last-`(seq-1)`-bytes context, so with drafting disabled the output is byte-identical to `stream()`. Byte-exactness under greedy is **proven on CPU**: a causal forward over `window ++ draft` is bitwise-identical at the window positions to `stream()`'s single-byte forward, so an accepted draft byte samples from the same distribution the one-byte path would. Measured CPU (chat80m, 121.8M, greedy): output bytes are IDENTICAL lookahead-on vs off vs `stream()`. A seeded CPU end-to-end parity test (`tests/mri/test_lookahead_parity.py`) pins this against an accept-loop or window regression on a prompt engineered to accept drafts. Throughput on/off: repetitive/quote prompt 1.82x (chat rep) / 4.94x (rep off); novel prompt 1.21x (chat rep) / 1.63x (rep off) — a speedup on novel text too, since a small byte model's greedy output is itself repetitive. The `no_repeat_ngram=16` chat guard only bans generated self-loops (the controller's history is generated bytes only, never the prompt), so quoting the prompt / RAG facts is fully draftable and caps accept spans only inside self-repetition. Emits coarse `fast_byte` events carrying the C path's core fields (`byte`, `argmax_byte`, `T`, `ms_per_byte`, `backend`) plus lookahead extras (`draft_len`, `accepted_extra_so_far`, `acceptance_rate`) that `collect`/`_local_delta_stream`/`_stop_on_bytes` render identically to `token` events; the full-telemetry `stream()` is unchanged for the `/generate` MRI view.

Pitfall: drafting is gated on device (`LOOKAHEAD_DEVICES = ("cpu",)`). The byte-exact argument holds bitwise only on CPU — an accepted draft runs the verify forward over `window ++ draft`, a longer shape than `stream()`'s per-byte forward, and on MPS float GEMMs over different shapes are not guaranteed bitwise-identical, so a near-tie argmax can flip. Off CPU the draft cap is forced to 0, so every forward keeps the single-byte-window shape and parity holds trivially (the fast path's telemetry savings remain). This is a deferred measurement, not a permanent limit: re-measure MPS lookahead-vs-`stream()` byte parity once the MPS device is free (a live 800M training run currently owns it); if it holds, add `"mps"` to `LOOKAHEAD_DEVICES` and re-enable drafting there.

Pitfall: the hybrid/patched trunk (chat80m: `VeritatePatched`, recurrent global mixer) has no `kv_cache_patch_attn`, so `KVCachedDecoder` (mode `kv`) does not apply and the verify is a full-window re-forward, not a KV/recurrent-state-cached one. A state-cached verify (draft-only incremental forward with rollback) needs a per-trunk streaming-state cache the patched/recurrent trunks do not yet expose; it is a model-side addition, not a decode-loop change.

- [agent/](../../../veritate_mri/inference/agent/) — multi-step reasoning (chain-of-thought, tool use).
- [addons/](../../../veritate_mri/inference/addons/) — pluggable behaviors (embeddings, classification heads).

Held under `app.config["BRAIN"]`. Loaded eagerly at startup if `pytorch_load_mode="always"`; lazily on first `/generate` if `on_demand`. The idle watcher unloads it after `pytorch_idle_unload_secs` of inactivity in `on_demand` mode. The checkpoint read uses `torch.load(..., mmap=True)` so the recurring reload after an idle unload pages weights lazily instead of copying the whole file (measured 14-25 s -> 0.5 s for the raw load of a ~1 GB checkpoint on CPU; values `torch.equal`-identical).

## Pitfalls

- `BRAIN` is a single-instance global. Two simultaneous `/generate` calls serialize on the brain lock.
- Switching models reloads — first request after a switch is slow.
- The brain holds GPU memory while loaded; long idle periods on a shared GPU machine should use `on_demand` to release memory automatically.
- Attention panels are empty by design for recurrent-mixer layers: the telemetry loop skips layers whose captured qkv length != T (recurrent blocks pad to CHUNK=64 internally, so per-position attention weights do not exist) and appends an empty per-layer entry instead.
- Non-canonical trunks have no engine `.bin` path, so they serve CPU-only through the brain: ~1 B/s at 121M with full telemetry. The fast path for research trunks is a future engine format.
