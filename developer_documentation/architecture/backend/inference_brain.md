# inference_brain (PyTorch)

## What it is

The PyTorch inference path used by the Generation tab. Lives under [veritate_mri/inference/](../../../veritate_mri/inference/). Co-exists with the C engine — selectable per request.

## How it works

- [pytorch.py](../../../veritate_mri/inference/backends/pytorch.py) — loads a `.pt` checkpoint, holds the model in memory with a lock for thread safety. Reloaded on model switch or idle-unload.
- Model construction goes through [veritate_core/load.py](../../../veritate_core/load.py)`::load_from_state_dict`, the single sanctioned branch point (preflight 11a). It dispatches on the checkpoint's `training_args.trunk`: `dense` takes the canonical path; `patched`/`hybrid`/`hybrid_moe`/`looped`/`recurrent` build the research trunk classes (`state_rule` threaded, `strict=True` load). The brain therefore serves research-trunk checkpoints (e.g. hybrid chat models) through `/generate` unchanged.
- [decode/](../../../veritate_mri/inference/decode/) — decoding strategies: greedy, nucleus sampling, temperature schedule. Per-token telemetry emission for the dashboard.

### Device (CPU / GPU)

The brain picks its device from `VERITATE_INFER_DEVICE` (`auto` | `cpu` | `mps`) via `_pick_infer_device`; `auto` takes MPS (Apple GPU) when available, else CPU. `/meta` reports the live device as `pytorch_device` and the dashboard shows it as a `device` chip. Weights run in fp32 on either device, so greedy decodes are byte-identical CPU vs MPS (verified 40/40 on the 200M hybrid); MPS wins because the per-byte forward is FLOP-bound.

The split that makes the GPU actually help: the **forward runs on the device**, but **per-token telemetry runs on CPU**. Each MRI frame is hundreds of small ops with `.item()`/`.tolist()` syncs, which stall the GPU far more than they cost on CPU (an all-on-device build measured *slower* than pure CPU: 257 vs 149 ms/byte on the 200M). So captured activations are batch-moved to CPU once after each forward (`_captures_to_cpu`, one sync point, not per-block inside the hooks), and the derived tables (`byte_direction`, `W_E_T`, `emb_w`) plus `last_logits` are kept CPU-side. Net on the 200M: forward 3.5x faster on MPS (40 vs 142 ms/byte), full-MRI stream 2.3x (65 vs 149). `PYTORCH_ENABLE_MPS_FALLBACK=1` is set as a safety net for any op without an MPS kernel; the hybrid recurrent forward uses only MPS-native ops today, so it is not exercised on the hot path.

### Repetition control

[decode/repetition.py](../../../veritate_mri/inference/decode/repetition.py)`::RepetitionController` is the shared byte-level loop guard, applied in both `Brain.stream` and every `stream_fast` submode (through `_sample_one`). Two mechanisms over a sliding window of the last `rep_window` generated bytes:

- **no-repeat-ngram (hard ban).** A candidate byte that would complete an `no_repeat_ngram`-byte sequence already emitted verbatim is masked to `-inf` before top-k. At byte level `n ~ 16` blocks verbatim phrase loops; single-byte penalties are too crude (every byte recurs).
- **suffix-repeat penalty (soft).** A byte that extends the current longest verbatim suffix run (length `>= REP_MIN_MATCH = 4`, below the ngram threshold) is demoted by `rep_penalty * (run - min_match + 1)` nats on the selected top-k logits. Applied post-temperature so the demotion factor `exp(-p)` is scale-free — identical across the PyTorch and C samplers despite their different raw-logit scales.

Defaults (chat): `rep_window=256`, `rep_penalty=0.5`, `no_repeat_ngram=16`. Threaded from `/generate` (`rep_window`/`rep_penalty`/`no_repeat_ngram`), on for chat mode, off (all zero) for autocomplete. With everything off the controller is a no-op and sampling is bitwise-identical to the pre-feature path (parity preserved). The C engine sampler ([model.c](../../../veritate_engine/v1/src/model.c)`::sample_token_ext`) mirrors this algorithm and constants byte-for-byte; keep the two in sync.

### Chat turn-stop

`/generate` wraps BOTH backend streams (the PyTorch `Brain.stream`/`stream_fast` generator and the C `_c_engine_stream`) in the same `_stop_on_bytes(gen, _chat_stop_seq(prompt))` at the route level ([backends_routes.py](../../../veritate_mri/routes/backends_routes.py)), so chat stop behavior is identical across C and PyTorch — a single source of truth, no per-backend divergence. For a framed prompt the wrapper halts at the FIRST turn marker (`<|end|>`, `<|user|>`, `<|assistant|>`; ChatML `<|im_end|>`/`<|im_start|>`) and emits a synthetic `stop` event carrying the marker in `reason`. The multi-marker set matters because the multi-turn SFT model frequently opens a next `<|user|>` turn without first emitting `<|end|>`; watching only `<|end|>` let the whole self-conversation stream. The C `chat_traced` subprocess keeps generating internally after the route stops pulling; `CTracedSubprocess._drain_to_tend` ([c_engine.py](../../../veritate_mri/inference/backends/c_engine.py)) drains the buffered frames + `TEND` (or kills+respawns) so the next request starts on a clean pipe. `/hybrid/chat` reuses the same wrapper in `_generate_local` for an early stop, then `_trim` does the final cleanup.

Serving splits on a per-request trace flag over the one shared subprocess (no second model load): `_c_engine_stream(..., trace=...)` threads `do_trace` into the header and dispatches on the frame marker. Fast is the default (`trace=False`): the engine runs `chat_traced` with tracing off, emits coarse 16-byte `FFRM` frames, and `_c_engine_stream` yields `fast_byte` events that `collect`/`_local_delta_stream`/`_stop_on_bytes` render identically to `token` events. Only the `/generate` MRI view opts into `trace=True` for the full `TFRM` per-byte telemetry (`_build_c_mri_frame`). So the chat no longer pays the logit-lens matvec + DLA-scan cost when nobody is watching the MRI; output bytes are identical to the traced path for the same request (see [veritate_engine.md](veritate_engine.md)).
- [agent/](../../../veritate_mri/inference/agent/) — multi-step reasoning (chain-of-thought, tool use).
- [addons/](../../../veritate_mri/inference/addons/) — pluggable behaviors (embeddings, classification heads).

Held under `app.config["BRAIN"]`. Loaded eagerly at startup if `pytorch_load_mode="always"`; lazily on first `/generate` if `on_demand`. The idle watcher unloads it after `pytorch_idle_unload_secs` of inactivity in `on_demand` mode.

## Pitfalls

- `BRAIN` is a single-instance global. Two simultaneous `/generate` calls serialize on the brain lock.
- Switching models reloads — first request after a switch is slow.
- The brain holds GPU memory while loaded; long idle periods on a shared GPU machine should use `on_demand` to release memory automatically.
- Attention panels are empty by design for recurrent-mixer layers: the telemetry loop skips layers whose captured qkv length != T (recurrent blocks pad to CHUNK=64 internally, so per-position attention weights do not exist) and appends an empty per-layer entry instead.
- Non-canonical trunks have no engine `.bin` path, so they serve CPU-only through the brain: ~1 B/s at 121M with full telemetry. The fast path for research trunks is a future engine format.
