# hybrid chat (front-door chat endpoint)

## What it is

The chat endpoint behind the `/` front door. Lives at [veritate_mri/routes/hybrid_routes.py](../../../veritate_mri/routes/hybrid_routes.py). It answers a user message with a model the user selects: a locally trained model on the PyTorch or C engine, the public Carpathian model, a configured teacher provider, or an installed Ollama sub-model. Any of them can carry multi-turn conversation context (with automatic compaction) and be grounded with the local knowledge base. Served to users at `/` and `/chat` (page `veritate_mri/web/hybrid.html`).

## How it works

`POST /hybrid/chat` resolves the request body: `model`, `backend` (`pytorch` | `c`), `use_rag`, and the conversation memory (`history` + `summary`).

1. **Routing.** `_resolve_route(model, backend)` returns a uniform `complete(messages, system) -> text` for the selected model, plus its label, response-backend, and kind (`remote` | `local`). `teacher:<provider>:<model>` routes to that provider/model (the model name may contain colons; the id is split on the first colon after the prefix). The bare `teacher` id routes to the active teacher in Settings (legacy). `is_local_model(name)` ([hybrid_routes.py](../../../veritate_mri/routes/hybrid_routes.py)) runs a locally trained model. Anything else (empty, `cloud`, unknown) is the public Carpathian model. A route raises `ChatUnavailable` for an expected failure (bad key, unreachable host, nothing configured), mapped to 503.
2. **Retrieval (opt-in), every model.** When `use_rag` is set and the knowledge base has files (`has_corpus()`): BM25 over the corpus returns the top-`k` chunks (`TOP_K = 3`), each capped at `KB_CHUNK_PREVIEW` bytes. Pure local lexical search, no embedder, no external service. `kb_scope` selects which corpus: `all` (platform + user, default), `platform` (shipped Veritate docs only), or `user` (uploads only). Facts ground **every** route, not just local models: `_system_text` frames them in the system prompt for remote models (prefixed by `CHAT_SYSTEM`) and as a `context:` block for local byte models with NO persona line: identity is trained into the model from step 0, and an injected persona in the `context:` channel made the byte model recite its identity every turn instead of answering (removed 2026-07-13). For local models `_fit_local_system` budgets the rendered prompt to the model's trained `seq` minus the `MAX_NEW` reply headroom (the raw `TOP_K` × `KB_CHUNK_PREVIEW` facts would overflow seq-1024, where the C engine returns zero bytes on an over-length prompt): fact previews shrink evenly, then the lowest-scoring facts drop (a fact below `LOCAL_FACT_MIN_CHARS` is dropped rather than truncated further), then the summary tail-trims; the chat markers, history, and user message are never trimmed. The UI `sources` keep the full previews — only the model's facts slice is budgeted. The chat-page **Veritate (platform docs)** pick is the special model id `veritate_docs`: the route maps it to the public model with `use_rag` forced and `kb_scope="platform"`, labelled `Veritate (platform docs)` (it is not a backend model of its own). Recent Training-tab log lines (`training_log_lines()`: in-memory ring entries from sources `plugin`, `plugin:<id>`, `save`, tailed to `TRAIN_LOG_TAIL`) are folded into the grounding whenever `use_logs` is set or in `veritate_docs` mode, so the assistant can answer questions about a run. The chat page exposes this as a **Read my recent training logs** checkbox.
3. **Conversation memory + compaction.** The client carries the conversation as `{summary, turns}` and sends it each turn. After answering, `_compact` bounds the memory to the selected model's character budget (`context_limit_chars`). The strategy is model-aware because a small byte model cannot summarize its own history:
   - **Local byte model** (`kind == "local"`): it *slides*. `_fit_tail` keeps the newest whole turns that fit `char_limit` (opening on a user turn, always at least the final turn) and drops the older ones; the summary is cleared (no `SUMMARY_SYSTEM` call: an 80M byte model's self-summary is garbage). Mechanical, deterministic, no model call, so the memory is always bounded to the window and the next prompt never overflows the model's trained `seq` (an over-length prompt makes the C engine return zero bytes).
   - **Remote (cloud/teacher):** it *summarizes*. Older turns fold into the running summary via the selected model (`SUMMARY_SYSTEM`), keeping the last `CTX_KEEP_TAIL_TURNS` verbatim; best-effort, a failed summarize leaves history intact.

   The updated memory plus a `context` gauge (`_context_meter`: `{turns, chars, char_limit, pct}`, `pct` 0..1) are returned for the client to store and render. Because a local slide runs every turn the memory exceeds budget, the gauge settles at or below 100% instead of climbing past it.

   **Model-aware budget.** `context_limit_chars(kind, provider, model)` sizes the memory budget to the model: a local byte model uses its trained `seq` (chars == bytes, e.g. 1024); cloud/teacher use a nominal per-provider window (`CONTEXT_TOKENS_BY_PROVIDER` × `CHARS_PER_TOKEN`), scaled by `CONTEXT_MEMORY_FRACTION` to reserve room for the preamble, facts, question, and reply. The OpenAI-compatible gateway does not report a model's real window, so cloud/teacher values are nominal model-family sizes and a host's actual served limit (e.g. an Ollama `num_ctx`) may be lower.
4. **Generation.** `complete(messages, system)` runs the selected route:
   - Remote (cloud/teacher): a messages list (`history` + the new user turn) plus the system preamble. Cloud goes through `ai_assist.chat`; teachers through `teacher.client.complete` with that provider's key + base url from `teacher_configs[provider]` (falling back to the flat `teacher_*` slots and `VERITATE_TEACHER_API_KEY` for the active provider).
   - Local: `_render_local` builds a multi-turn byte prompt (prior turns in chat markers, the final turn via `build_prompt` / `build_plain_prompt`); `_ensure_pytorch` / `_ensure_c` load the model and `_generate_local` decodes via `brain.stream` / `_c_engine_stream`. The C path serves through the non-traced fast engine mode by default (`_c_engine_stream` defaults `trace=False`, so the chat never pays for the MRI logit-lens/DLA telemetry the `/generate` full-glass needs); it streams coarse `fast_byte` events that `collect` renders byte-for-byte identically to the traced `token` events (see [inference_brain.md](inference_brain.md)). Both branches pass the chat repetition defaults (`REP_WINDOW_DEFAULT` / `REP_PENALTY_DEFAULT` / `NO_REPEAT_NGRAM_DEFAULT` from `inference.decode`, i.e. 256 / 0.5 / 16) so a byte-level model does not fall into `"complex and complex and…"` loops; `/generate` keeps its absent-params-default-OFF contract, but this chat path is always framed so it always wants the guard on. `_generate_local` wraps the stream in `_stop_on_bytes(events, _chat_stop_seq(prompt))` (the same route-level early-stop as `/generate`, halting at the first turn marker so generation ends instead of running to `MAX_NEW`). `collect()` joins the `token` / `fast_byte` bytes; `_trim()` runs `_sanitize_text` (restores the C wire newline `0x01` → `\n`, drops every other control byte except tab/newline so the answer is clean text and valid JSON) then cuts at the first stop marker (`<|end|>`, `<|user|>`, `<|assistant|>`, `\ncontext:`). `_local_events(cfg, backend, prompt, mri=False)` owns the stream + stop-marker construction, shared by the buffered `_generate_local`, the true-token OpenAI path, and the `/hybrid/chat/stream` path below; its `mri` flag selects the full-telemetry path (see Per-request MRI telemetry below).

### Streaming (`POST /hybrid/chat/stream`)

The chat-page streaming twin of `/hybrid/chat`: same body, same routing and grounding, but the reply is delivered as an SSE `text/event-stream` so it paints token-by-token like the Generation tab instead of blocking on the whole answer. Both endpoints share `_chat_prepare(cfg, body)` (parse body + retrieve + `_resolve_route`, returns a `_ChatCtx` or `None` for an empty message) and `_chat_result(ctx, answer)` (fold the new turn into the compacted memory, build the response dict), so a streamed reply and a buffered reply are framed identically. `_hybrid_stream_response` emits one `{"kind":"delta","text":...}` frame per decoded segment via `_chat_delta_stream`, then one terminal `{"kind":"done", ...}` frame carrying the same `{answer, model, backend, confident, sources, memory, context}` payload the buffered route returns. `_chat_delta_stream` honors the selected engine: a **local** model decodes true per-token on the chosen engine (`_ensure_c` / `_ensure_pytorch` then `_local_events(cfg, backend, ...)` → `_stop_on_bytes` → `_local_delta_stream`, the same generator `/generate` and the OpenAI path use); a **remote** model runs the buffered `complete()` then chunks the answer word-by-word on `CHAT_STREAM_SPLIT`. A generation failure after the stream has opened surfaces as a single `{"kind":"error","error":...}` frame (status is already 200); an empty message is still a pre-stream 400. Unlike the true-token OpenAI path, this path keeps RAG/KB grounding, conversation memory, and the context gauge — the chat page needs all three.

### OpenAI gateway (`POST /v1/chat/completions`)

Same routing as `/hybrid/chat` (`_resolve_route`), OpenAI wire envelope. `_openai_messages_in` folds `system` turns into the system string and validates the conversation. Non-stream returns a `chat.completion`. Streaming splits on `kind`: **local** trained models stream true per-token via `_openai_stream_local` (a role frame, then a `chat.completion.chunk` content delta per decoded segment as the model generates it, a `finish_reason:"stop"` frame, then `data: [DONE]`); **cloud/teacher** keep the buffered `_openai_stream` (the non-streaming `complete()` runs to completion, then the answer is chunked word-by-word on `CHAT_STREAM_SPLIT`). `_local_stream_items(events, emit_frames=False)` drives the local path (its text-only view `_local_delta_stream` is what the non-MRI stream consumes): it decodes token bytes incrementally as UTF-8 (a `codecs` incremental decoder, so multi-byte characters never emit a partial replacement char), sanitizes, and holds back a `STOP_HOLD`-char tail so a forming turn marker is cut by `_stop_on_bytes` before any of it streams; a trailing flush emits the trimmed remainder. RAG/KB grounding is **not** wired into the true-token path: the local model runs on the OpenAI `messages` + `system` only. The gateway accepts `temperature`/`max_tokens`/`top_k` for compatibility but the wrapped generation fixes them. An OpenAI client cannot pass a `backend`, so the gateway picks one per model via `_default_local_backend`: the compiled **C engine** when the model has a `.bin` and the engine binary is built (fast, CPU subprocess, so it does not contend with an MPS training run), else the **PyTorch** brain for non-exportable trunks (recurrent/RoPE/MTP). This mirrors the dashboard's `effectiveBackend()` and `/generate`'s C default; the earlier hardcoded PyTorch default stranded C-capable models (chat80m, chat200m) on the CPU-slow PyTorch decode.

### Per-request MRI telemetry (`mri:true`)

`/hybrid/chat`, `/hybrid/chat/stream`, and `/v1/chat/completions` take an opt-in `mri` boolean (`MRI_KEY`) that returns the per-byte MRI frames the `/generate` interpretability view consumes. Absent or false is the default and byte-for-byte the fast, non-traced serving above. It applies to **local** models only; a remote route ignores it (no per-byte telemetry to emit), so the response is identical to leaving it off. The flag selects telemetry, never sampling: `_local_events(cfg, backend, prompt, mri=...)` threads it to `_c_engine_stream(..., trace=mri)` (the C engine's full `TFRM` frames vs the coarse `fast_byte` fast path) or to `_pytorch_mri_events` (`Brain.stream` full telemetry vs `Brain.stream_fast(mode="lookahead")`), both with the same sampling defaults — see [inference_brain.md](inference_brain.md) for the trace/full-vs-fast decode identity. The frames are the exact parsed objects the MRI view receives; fields are passed through unfiltered (preflight 23). Delivery:

- Buffered (`/hybrid/chat`, `/v1` non-stream): `_generate_local_mri` runs the traced/full stream once, capturing both the answer text and the frame list (`meta`, one `token` per byte, `stop`); the frames attach under a top-level `mri` key (`_chat_result(ctx, answer, frames)` / `dict(_openai_completion(...), mri=frames)`).
- Streaming (`/hybrid/chat/stream`, `/v1` stream): `_local_stream_items(..., emit_frames=True)` interleaves `("frame", ev)` with the text deltas. The `/hybrid` stream emits each frame raw (its native `kind:"meta"/"token"/"stop"`, distinct from the `kind:"delta"` text frames); the OpenAI stream wraps each frame in `_mri_chunk_frame` — a valid `chat.completion.chunk` with empty `delta` and the frame under a top-level `mri` key, so an off-the-shelf OpenAI client that reads only `choices[].delta.content` ignores it. The `done` frame does not repeat the inline frames.

Frames are large (hundreds of KB per generated byte from the C engine); request telemetry only when consuming it. `/generate` remains the native full-telemetry endpoint. Full request/response shapes in [external_api.md](../../../documentation/api/external_api.md).

The public model key is the `PUBLIC_AI_KEY` constant in [settings.py](../../../veritate_mri/runtime/settings.py), injected live by `settings.get()` (never persisted, so rotating it reaches every install on next load); a user-set `ai_api_key_user` overrides it. Generation reuses platform code; this module owns no decode loop and pins no model name. The corpus chunks + BM25 index are cached in `_STATE` and rebuilt on the next retrieve after an upload (`reset_index_cache`). The loaded model lives in shared app config (`cfg["BRAIN"]` / `cfg["C_SUBPROCESS"]`), the same state the platform backends use.

### Knowledge base

Retrieval spans two folders (`_corpus_files()`): the shipped `PLATFORM_KB_DIR` (`veritate_mri/data/platform_kb`, committed to the repo) and the user's `KB_DIR` (`veritate_mri/data/kb`, gitignored uploads). The platform KB carries the Veritate documentation, so a fresh install can ground answers about the platform with no upload; `has_corpus()` is true whenever either folder has files. `kb_files()` counts user uploads only (the upload UI's file count). `_kb_chunks()` reads every file across both folders and splits it with the platform retriever's whitespace-aware `_split_chunks`; `_kb_index()` builds a `BM25Index` ([inference/agent/tools/retriever.py](../../../veritate_mri/inference/agent/tools/retriever.py)) over those chunks. No Ollama, no embeddings, no `.npz`. To revise the platform answers, edit the markdown in `platform_kb/`.

### Chat page UI

The page ([veritate_mri/web/hybrid.html](../../../veritate_mri/web/hybrid.html)) is a self-contained dark page with the platform `V·E·R·I·T·A·T·E` logo. A `settings` toggle opens an inline panel (with a **Close settings** button along its bottom, `#settingsClose`) holding three sections:

- **Model** select: grouped `optgroup`s. A `Veritate` group with **Veritate (platform docs)** (value `veritate_docs`, the default selection for a fresh visitor) — chat grounded on the shipped platform KB. Then `Local (trained)` from `/pytorch-models`; then one group per remote source from `/hybrid/models` — `Cloud` (the `Carpathian AI (public)` entry, value `cloud`), plus a group per configured teacher provider. API providers contribute their saved model; local providers (Ollama, LM Studio, llama.cpp) are enumerated live so every installed sub-model is listed. Each remote entry's value is its `teacher:<provider>:<model>` id. A `Train your own →` link points to `/app#training`. Selecting a remote model hides the engine section; the `veritate_docs` pick also hides the knowledge section (its grounding is implicit). A spinner (`.spin`) shows in the pending reply bubble until the first streamed `delta` replaces it.
- **Engine** segment: `PyTorch` / `Veritate (C)`. The C button is disabled for models without a `veritate.bin` (cross-checked against `/c-models`), with an inline hint. The choice is **per model** (`state.engines[model]`, persisted) and **defaults to the fast C engine whenever the model has a `.bin`** (`effectiveBackend()`), falling back to PyTorch only when it has none. A saved C pick is never silently downgraded to PyTorch just because the `/c-models` list has not loaded yet — the earlier global `state.backend` clobbered the pick under that race and stranded a C-capable model on the (CPU-slow) PyTorch engine.
- **Context** section (shown for every model except the `veritate_docs` pick, which grounds implicitly): **Use my uploaded files when answering** (`#ragChk`, disabled until the corpus has files), **Read my recent training logs** (`#logChk` → `use_logs`), and a file uploader that posts to `/hybrid/kb/upload`. Upload is instant (no embedding); the page then refreshes `/hybrid/health` and enables grounding.

A header **new chat** button clears the conversation memory and the transcript. A small SVG **context ring** (`#ctxArc`, with the percentage in its center) sits in the chat input bar and fills toward the model's context budget from the response's `context.pct`; clicking it opens a popover (`#ctxPop`) explaining the gauge and showing the live `chars / char_limit`. It is driven entirely by the server meter (no client-side estimate), so it reads 0% until the first reply of a session. Opening settings blurs the chat behind it (`#settings.open ~ .wrap`). A **spinner** shows in the pending bubble until the first streamed `delta` arrives. **Slash commands** (`handleSlash`): `/new`, `/model <name>`, `/rag on|off`, `/help` — parsed in-page, no backend call. Settings persist in `localStorage` under `veritate_chat_settings_v1`; the conversation memory `{summary, turns}` persists under `veritate_chat_convo_v1`. Each send posts `{message, model, backend, use_rag, use_logs, history, summary}` (`backend` = `effectiveBackend()`) to `/hybrid/chat/stream` and reads the SSE body: each `delta` frame appends to the reply bubble live, and the terminal `done` frame (`applyDone`) replaces the stored memory, updates the ring from `context`, and renders `sources` only when retrieval returned any. While a reply streams the **Send button becomes Stop** (`onSend` → `AbortController.abort()`); aborting closes the connection, which propagates `GeneratorExit` through the stream generator so the C subprocess drains/kills (`_drain_to_tend`) and frees the CPU instead of running to `MAX_NEW`. A stopped reply keeps its partial text and records the turn locally (no server `done`/compaction fires on abort). The dashboard Chat tab ([chat_tab.js](../../../veritate_mri/web/chat_tab.js)) shares the identical flow.

## Endpoints

- `GET /hybrid/health`: returns `{ok, has_corpus, n_files}`. The chat page uses `has_corpus` to gate the retrieval checkbox.
- `GET /hybrid/models`: returns `{models: [{id, label, group, provider?, model?}]}` — the public model plus every configured teacher's selectable models (local providers enumerated live with a short `ENUM_TIMEOUT_S` so a down host can't stall the picker). Fetched in parallel with the model lists on page load.
- `POST /hybrid/kb/upload`: multipart `file`. Saves it into `KB_DIR` (sanitized name, `.txt` default), clears the index cache, and returns `{ok, filename, n_files, n_chunks}`. Rejects no-file with 400 and oversize (> `UPLOAD_MAX_BYTES`) with 413.
- `POST /hybrid/chat`: body `{message, model, backend?, use_rag?, use_logs?, kb_scope?, k?, history?, summary?}`. `model` may be a local name, `cloud`, `teacher:<provider>:<model>`, or `veritate_docs`. `use_logs` folds recent training logs into the grounding. `kb_scope` is `all` | `platform` | `user`. `history` is the prior `[{role, content}]` turns (capped at `HISTORY_MAX_TURNS`); `summary` is the running compaction summary. Returns `{ok, answer, model, backend, confident, sources, memory, context}`. `memory` is the post-turn `{summary, turns}` the client stores for the next request; `context` is the gauge `{turns, chars, char_limit, pct}` (`char_limit` is model-aware); `sources` is `[{text, score}]` (RAG hits carry a score, folded-in training-log lines carry `score: null`). Empty message → 400; an unavailable model (bad key, unreachable host, nothing configured) → 503; unexpected generation failure → 500.
- `POST /hybrid/chat/stream`: same body as `/hybrid/chat`; the SSE (`text/event-stream`) streaming twin the chat pages use. Emits `{kind:"delta", text}` frames as the model generates (true per-token for local models on the selected engine, word-chunked for remote), then one `{kind:"done", ...}` frame carrying the same `{answer, model, backend, confident, sources, memory, context}` payload as `/hybrid/chat`. A mid-stream failure is a `{kind:"error", error}` frame (status already 200); an empty message is still a pre-stream 400.

These are public (auth gate exempts the `/hybrid` prefix and `/`). See [auth.md](auth.md).

## Dependencies

- For local generation: a trained model with a checkpoint (PyTorch) or a `veritate.bin` export plus a built C engine (C). Model lists come from `/pytorch-models` and `/c-models`.
- For retrieval: nothing external. Pure-Python BM25 over the uploaded `KB_DIR` files.
- For the public model: the public Carpathian key constant `PUBLIC_AI_KEY` in [settings.py](../../../veritate_mri/runtime/settings.py) (base `https://api.carpathian.ai/ai/v1`), injected by `settings.get()` and called via [ai_assist.py](../../../veritate_mri/runtime/ai_assist.py). A user-set `ai_api_key_user` overrides it.
- torch and the c engine subprocess (lazy-imported, only for local generation).

## Pitfalls

- BM25 is lexical: it matches on shared keywords, not paraphrase. Retrieval quality comes from the uploaded corpus, not a fancy ranker.
- The C engine option requires a `veritate.bin` export and a built engine binary. The chat page disables C for models without a `.bin` (via `/c-models`); a missing engine binary surfaces as a 503 from `_ensure_c`.
- Switching the selected model swaps the shared `cfg["BRAIN"]` / `cfg["C_SUBPROCESS"]`, the same slots the platform tab uses; the last-loaded model is the current one for both surfaces. Exception: models in the C-engine warm pool. `_ensure_c` calls `warm_select` first, so a switch to a warm-pinned model re-points `cfg["C_SUBPROCESS"]` at the resident subprocess instead of spawning, and a warm-pinned *outgoing* model is never closed on switch (only a non-pinned single-slot subprocess is). Switching between two pinned models is instant. See [warm_models.md](warm_models.md).
- The public model key is the `PUBLIC_AI_KEY` constant, injected by `settings.get()` and not persisted. Rotating it in source reaches every install on next load; a stale copy can no longer be stranded in `mri_settings.json`. A user-set `ai_api_key_user` still overrides it.
- The corpus + BM25 index are cached in `_STATE`; uploads clear the cache, but editing `KB_DIR` files on disk out-of-band needs a server restart (or another upload) to take effect. To make the chat answer questions about Veritate itself, drop platform docs into `KB_DIR` (`veritate_mri/data/kb`) and turn on grounding.
- Conversation memory is client-held: the chat page sends `history` + `summary` and stores the returned `memory`. The server is stateless across turns. A remote compaction turn spends one extra model call to summarize; a local model instead slides (drops the oldest turns, clears the summary, no model call) because a byte model can't summarize itself, so local memory is a recent-turns window rather than a summary.
