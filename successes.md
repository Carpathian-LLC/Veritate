## 2026-07-25: model growth (Net2Net FFN widen) is a real 3.6x step-lever on the hybrid trunk — but only nets compute if the small-model phase stops at saturation

- Tested: IDEA 9's growth-coupled-curriculum bet. Arm A GROWN = `conceptsho_10m` step 2000 (15.99M, hybrid trunk) widened ffn 1280->2560 via `stretch_ffn_state_dict` (`experiments/v2/upcycle/`) to 25.74M, then 1000 steps on a harder stage-2 curriculum. Arm C SCRATCH = same 10m_w2 shape from random init, 1000 steps on the same corpus. Identical batch 64 / bf16 / muon / constant LR 4e-4 / eval grid 50. Sequential, dashboard-launched. Metric and gates pre-registered in ideas.md BEFORE arm C ran (threshold defined as a protocol — T = arm A's val at its 250th stage-2 step = 0.121434 — not a hand-picked number).
- **Function-preserving growth VERIFIED on the hybrid trunk, which the upcycle kit was never written for** (it targets the deleted `veritate_800m` dense plugin; its `_smoke.py` and model-level wrappers are dead code, but the state_dict-level functions are pure tensor ops and work). Static check: new `ff.down` columns exactly 0.0 and old columns bit-exact vs parent, all 12 blocks. Dynamic check: **resume loss 0.0917 vs the parent's final 0.0923 — no spike.** Depth-stacking was rejected on purpose: the hybrid assigns a subset of blocks as global mixers by a pattern derived from layers/n_global, so duplicating blocks would scramble local-vs-global assignment.
- **Result — steps-to-target, whole-curve shift (the pre-registered ladder, not one crossing):** 0.30 -> A 50 / C 450 (9.0x); 0.20 -> 100 / 500 (5.0x); 0.15 -> 100 / 550 (5.5x); **T=0.1214 -> 250 / 900 (3.6x)**. `S_C=900 >= 500` clears the PASS gate. C never catches A inside 1000 steps (0.1208 vs 0.1185).
- **The honest counter-result, from a falsifier registered next to the gate: in TOTAL compute growth LOST.** Params x steps: A = 2000x15.99M + 250x25.74M = 38.42 G; C = 900x25.74M = 23.17 G. **A cost 1.66x MORE.** The 3.6x is denominated in large-model steps only; the stage-1 phase is not free. Break-even stage-1 budget = **1046 small steps**; stage 1 saturated at ~1250 and I ran 2000, overspending the cheap phase by ~950 steps and turning a likely net win into a 1.66x loss.
- Meaning: growth is a genuine lever and the mechanism is validated on our actual architecture — but the operative rule is **stop every curriculum stage at its saturation point.** The speedup is real in the currency that matters for a flagship pretrain (expensive large-model steps), and it is recoverable here: had stage 1 been cut at ~1000 steps, total compute would have favoured growth. This is directly actionable for the flagship: run early stages small, watch val, cut the moment it flattens, widen, continue.
- Honest boundaries: ONE growth technique (ffn widen; depth/hidden/MoE untested on hybrid), ONE size step (16M->26M), ONE corpus, single seed, no repeat runs — the 3.6x has no error bar. The corpus is synthetic and SATURATING, so this measures approach RATE to a shared floor, not final quality; final val differs by only 0.0023. Warmup asymmetry noted and judged correct rather than corrected: C pays 150 warmup steps at 26M, A paid its warmup during stage 1 at 16M — doing early instability cheaply IS the growth thesis, so charging C for it is realistic.
- Run: `models/conceptsho_grown/` (step 3000) vs `models/conceptscratch_10m_w2/` (step 1000); corpus `trainers/corpus/concepts2_ho_{train,val}.bin`; generator `veritate_mri/tools/build_curriculum_corpus.py --stage 2`; trainer size `10m_w2` added to `trainers/veritate_10m/manifest.json` (pure addition, upstream mirror pending). Full pre-registration + gates in ideas.md IDEA 9.

## 2026-07-20: c_engine.py `_last_clean` invariant bug — audited + fixed; a plausible-but-unproven root cause for the "chat template tokens bleed into response" symptom that a server restart resolved

- Tested: hypothesis from user chat log ([cardinal_chat.md](cardinal_chat.md)) that the C-engine subprocess was leaking stale stdout frames from an abandoned prior request into a subsequent request's response, causing the assistant to emit chat-template tokens (`<|end|>`, `<|user|>`, `<|assistant|>`) as content. Symptom cleared on server restart; recurred later; observed on BOTH Mac (`200m_m3` session) and Cardinal (`chat200m(SFT)_i7`), which ruled out hardware-specific corruption and pointed at engine/state.
- Audit method: traced every return/raise path in `CTracedSubprocess.stream()` ([veritate_mri/inference/backends/c_engine.py:306-511](veritate_mri/inference/backends/c_engine.py#L306-L511)) and verified the `_last_clean` invariant: **False during any active generation, True ONLY after a confirmed TEND marker**. `_last_clean = True` is the signal that the subprocess is idle and safe to reuse; False forces `_kill_and_respawn()` on the NEXT request (line 346-347).
- **BUG found — write-retry respawn leaks `_last_clean = True` into the retry generation.** Path ([c_engine.py:383-391](veritate_mri/inference/backends/c_engine.py#L383-L391)):
  1. `stream()` sets `_last_clean = False` at line 348 (correct).
  2. `stdin.write(header)` throws `BrokenPipeError` (subprocess died mid-write).
  3. Except block calls `self._spawn()` at line 385.
  4. `_spawn()` sets `self._last_clean = True` at line 300 (correct for a first-time-startup path, since a fresh proc IS clean).
  5. Retry write succeeds → enter the read loop with **`_last_clean = True`** (WRONG for a mid-generation state).
  6. Client abandons mid-generation → `finally` runs `_drain_to_tend()` at line 509.
  7. If drain exits WITHOUT reaching TEND — via `_read_exact` returning None (line 543/550/551), or bad marker (line 552-553 `else: return`), or exception (line 555-556) — `_last_clean` is NEVER cleared from step 4.
  8. Next request enters `stream()`, sees `_last_clean = True`, **skips** the `_kill_and_respawn` at line 346-347, writes its header to a subprocess that still has un-drained frames from step 6 in its stdout buffer.
  9. Next request's `_read_exact` at line 408 reads THOSE STALE FRAMES as its own response → template-token bleed the user observed.
- **Fix (1 line at [c_engine.py:391](veritate_mri/inference/backends/c_engine.py#L391)):** after the successful retry write, restore `self._last_clean = False`. Reason: `_spawn()`'s True is correct at first startup (no pending generation) but wrong when it's called mid-request; the invariant must be re-established. Alternative refactor (make `_spawn` not touch `_last_clean`, force all callers to set it) is cleaner but more invasive; chose the minimal fix for a shippable patch.
- Confirms restart-fixes-it symptom: a fresh process resets the in-memory `_last_clean` flag AND wipes any un-drained stdout, so the very first request after restart lands on a clean pipe regardless of what the buggy path did to the flag.
- Ruled out (not the bug): state cache (twin-hash + shape guard + FNV(path+size+mtime) model_id makes cross-restore ~2^-64 unlikely; snapshots store at prompt-end, before generation, per [model.c:537](veritate_engine/v1/src/model.c#L537), so they cannot include prior assistant-turn tokens). Warm-model residual state (`hybrid_reset` runs per-request when state cache misses, per [model.c:741](veritate_engine/v1/src/model.c#L741)). Cross-model swap (each `/backends/c load` respawns the subprocess).
- Honest boundaries: fix is applied LOCALLY only ([veritate_mri/inference/backends/c_engine.py](veritate_mri/inference/backends/c_engine.py)); Cardinal's checkout may or may not be at HEAD (needs `git pull` + backend restart there to deploy). No regression test added yet — the natural test is a fault-injection unit test that patches `stdin.write` to throw once on first call and asserts `_last_clean` is False after respawn; add before shipping to Cardinal. The observed bleed also had OTHER paths I audited as safe (Path C, D, E, F, G, H, I, J, K, L — all set `_last_clean` correctly), but I could not enumerate every possible interleaving; there may be adjacent bugs the same fault-injection test would catch. Minor observations not fixed this session: `_last_frame_time` is set at line 341 before prefill, so a slow-prefill request could false-trigger the STREAM_LOCK_TIMEOUT_S reclaim if prefill >30s (wren's ~1.8s TTFB is safe); `_drain_to_tend` calls blocking `_read_exact` whose deadline is checked only between iterations, so a hung subprocess can hang the drain until the outer STREAM_LOCK_TIMEOUT_S reclaim fires.
