## 2026-07-13: natural teacher-written queries measured — head transfer HOLDS but is retrieval-recall-bound (the last open boundary, now quantified)

- Tested: the boundary the entry below explicitly left open ("natural teacher-generated queries untested; chat200m can't produce them"). Used ollama qwen2.5:7b-instruct (Carpathian production model, read-only, zero training load) to generate 1211 natural (question, answer) pairs over 31 topics. Trained a fresh key head on 26 topics; measured retrieval + end-to-end on 5 FULLY HELD-OUT topics (nutrition_food, philosophy_religion, physics, programming, psychology) over the 1e5 fineweb store. Code `experiments/v2/memory/{make_teacher_pairs,eval_teacher}.py`.
- Retrieval (held-out topics, NATURAL queries): fineweb distractors baseline recall@1 0.152 / @5 0.234 -> trained 0.409 / 0.684; +train-facts (hard) baseline 0.135 / 0.228 -> trained 0.322 / 0.608. End-to-end (n=100, hard store): retrieval recall@1 0.300 -> grounded_acc 0.140 vs bare_acc 0.010.
- Meaning: the head transfer is REAL, not template memorization — ~3x baseline recall on natural free-form queries over topics it never trained on. BUT natural queries are ~2x harder than the heuristic "What is X?" queries of the entry below: hard-store recall@1 falls 0.50 (heuristic) -> 0.32 (natural). This is the honest recalibration downward, and it's now the measured wall. End-to-end grounding beats bare 14x (0.14 vs 0.01) but is only 14% absolute BECAUSE it is retrieval-recall-bound: recall@1 0.30 caps how often the right fact can reach the generator, so the bottleneck is retrieval on natural queries, NOT chat200m's answering.
- The cheap high-impact lever (in the data): recall@5 (0.61) is ~2x recall@1 (0.32). Injecting the top-5 leaves into context instead of top-1 roughly doubles the odds the fact is present, at ~5 short leaves against an 8k+ window = negligible cost. This is the first thing to wire when the memory system enters serving. Further recall gains: more training-topic diversity (diversity->transfer law), richer trunk features (the 800M when ready).
- Boundaries: single head, one model (chat200m); natural queries are teacher-generated (qwen), a proxy for real user questions; end-to-end answer quality is still chat200m's copy ceiling (the 800M is the fix). Run: `experiments/v2/memory/{make_teacher_pairs,eval_teacher}.py`.

Unseen (0.70) MATCHES seen (0.67): a head trained on 33 real topics generalizes to completely unseen real topics at full strength, a ~10x recall@1 lift over the raw baseline.
- Meaning: real-content retrieval WORKS and generalizes across topics. This resolves the toy-schema overfit (failures.md 2026-07-13) as a low-diversity artifact: 11 invented schemas gave weak transfer (0.33), but 33 diverse REAL topics give strong transfer (0.70) with no unseen-topic degradation, exactly as the diversity->transfer law predicted. The memory system is no longer validated only in-distribution on invented facts; it retrieves real facts across unseen real topics.
- Honest boundaries: queries are heuristic subject-extraction ("What is X?"), noisier than clean invented queries but easier than natural questions (natural teacher-generated queries untested; chat200m can't produce them); recall@1 0.70 / recall@5 0.92 (below the 0.97 of clean invented facts) reflects real ambiguity + heuristic queries. Under a HARDER distractor pool (1e5 fineweb + 4413 OTHER real facts) held-out-topic recall is recall@1 0.497 / recall@5 0.783 (`eval_real_hard.py`) -- lower than the fineweb-only 0.70/0.92 as expected (real facts are semantically-competitive distractors), still 7x over baseline (0.07) and usable (top-5 captures the fact 78% of the time on unseen topics). End-to-end ANSWERING on real facts not measured here (retrieval-only; the answer side is chat200m's copy limit -> the 800M). A bug was fixed en route: pooled_feats grouped by char length but batched by bytes, breaking on non-ASCII real text. Single run, one model.
- Run: code `experiments/v2/memory/{make_real_pairs,eval_real,eval_generalize}.py`; data `facts/canonical/*.jsonl`.

## 2026-07-13: FAISS IVF-PQ realizes the wall-time + memory win; trillion-character index feasible on-box

- Tested: FAISS IVF-PQ as the compiled ANN backend (the numpy drill-down, successes.md 2026-07-12, cut candidate count but LOST on wall-clock to a flat BLAS scan). Run torch-free (FAISS + torch each link libomp and DEADLOCK together at 0% CPU; head keys precomputed by dump_headkeys.py). Cosine via METRIC_INNER_PRODUCT on unit-norm keys. Code `experiments/v2/memory/eval_faiss.py`; faiss-cpu 1.14.3.
- Recall fidelity on the real 1e5 head-keys (exact = recall@1 0.976): IVF-Flat (full vectors) = recall@1 0.958 @ nprobe=64 (~1.8 pts off exact); IVF-PQ at 32 B/vec (32x compression) = recall@1 0.856 @ nprobe=64 (aggressive PQ on 256-d costs ~12 pts; a gentler m or a re-rank recovers most, not applied).
- Wall-time + memory (the win numpy could not deliver): flat vs FAISS-IVFPQ per-query = 1.08 ms vs 0.037 ms (29x) at N=1e6; 16.81 ms vs 0.109 ms (155x) at N=1e7. Speedup GROWS with N; PQ memory is 32x smaller (320 MB vs 10 GB at 1e7); build 68 s at 1e7.
- Meaning: the trillion-CHARACTER target is feasible on this box. A trillion chars ~= 500M leaves (~2 KB each); 500M x 32-64 B/key PQ = 16-32 GB RAM (fits) at sub-ms query. The sub-quadratic path is now wall-time real, not just candidate-count asymptotic. Boundaries: validated to 1e7 (the 500M-leaf build is an hours-long engineering run, unbuilt); PQ recall/memory is a knob (IVF-Flat 0.958 no-compression vs IVF-PQ 0.856 at 32x); fixed nprobe recall still drops with N (0.86@1e6 -> 0.775@1e7), nprobe must grow.
- Run: `experiments/v2/memory/{eval_faiss,dump_headkeys}.py`.

## 2026-07-12: sub-quadratic drill-down retrieval validated (IDEA 2 scale path toward a trillion)

- Tested: a pure-numpy hierarchical IVF drill-down (`experiments/v2/memory/hindex.py`: spherical-k-means coarse quantizer with n_cells ~ sqrt(N), probe the top-nprobe cells, exact-score only those) over the trained-head keys, to take the near-perfect flat retrieval (successes.md 2026-07-11) sub-linear. No FAISS (the design's licensed dependency-free fallback).
- Recall fidelity on the REAL 1e5 head-keys: flat exact = recall@1 0.976 / recall@5 0.998, scoring all 100.5k. Drill-down at nprobe=16 = recall@1 0.960 / recall@5 0.980 scoring 3155/query (3.1% of flat, ~32x fewer); nprobe=32 = recall@1 0.964 at 7.5%. Drill-down preserves recall within ~1.5 points of exact at ~30x less scoring.
- Sub-linear scaling on synthetic keys: candidates/query grew 5372 (N=1e5) -> 16995 (N=1e6), i.e. 3.16x for 10x data = exactly sqrt(N). Candidate cost is sqrt(N), sub-quadratic; scan-count speedup rises 19x -> 59x with N.
- Honest boundaries (measured): (1) WALL-CLOCK, not candidate count, inverts at these sizes: flat is one BLAS GEMM (0.88 ms/query at 1e6) and beats the Python-loop drill-down (4.42 ms). The candidate-count win is asymptotic; the wall-time crossover is above 1e6, and a production trillion-scale index needs a compiled backend (FAISS IVF-PQ) to realize it. (2) At fixed nprobe recall drops as N grows (synthetic 0.925@1e5 -> 0.785@1e6) because nprobe/n_cells shrinks; holding recall at scale requires nprobe to grow (slowly, still sub-linear). (3) This is CLUSTERED IVF, not the LEARNED drill-down navigator (the IDEA 2 research object); IVF already preserves recall, so the learned upgrade is optional headroom, not required.
- Meaning: the retrieval algorithm's cost is sqrt(N) with recall preserved to within ~1.5 points of exact on real keys. The sub-quadratic scale path from 1e5 toward a trillion is validated in principle; realizing the wall-time win at 1e9+ is a compiled-backend engineering step (FAISS), not a new research question.
- Run: `experiments/v2/memory/{hindex,eval_hindex}.py`.

## 2026-07-11: trained key head makes long-context needle recall WORK end-to-end (IDEA 2 milestone-1 cleared)

- Tested: the IDEA 2 addressable-memory gate on chat200m (270M, FROZEN), the retry of the zero-training baseline that failed the same gate (failures.md 2026-07-11; retry condition = a trained key head, now met). Byte-native key = mean-pooled trunk residual (new `hidden_states()` contract method on the hybrid trunk, `veritate_core/model_patched.py`) projected by a small MLP head (1024->512->256) trained with in-batch InfoNCE whose negatives are REAL store-distractor keys (so the head learns to beat fineweb leaves, not just other invented facts). Trunk frozen: the head trains on cached pooled features and applies to the cached 1e5 store keys with NO rebuild. Store = 1e5 512-byte fineweb leaves (~51M bytes, ~50M+ tokens of addressable context) built on MPS at ~26 leaf/s. Test = 500 held-out invented-entity facts (unseen entities); 100 generated. Code `experiments/v2/memory/`.
- Result (measured, single run): the trained head lifts retrieval from recall@1 0.40 / recall@5 0.71 (raw mean-pool) to recall@1 0.976 / recall@5 0.998 over the 1e5 store. End-to-end with single-leaf (top-1) context: retrieval recall@1 0.97, grounded answer accuracy 0.75, bare 0.02 -> margin 0.73. PASSES the pre-registered gate (>= 0.20 margin AND >= 0.60 floor), up from the zero-training 0.167. bare 0.02 confirms invented facts (no parametric leakage).
- What this proves: the >1M-token context works. A 270M byte model conditioning on a 51M-byte external store (50,000x its 1024-byte window) recalls a planted needle at 97% and answers it at 75%, vs 2% without retrieval. Retrieval is scale-stable (recall flat 1e3->1e5). Two levers closed the gate: a trained contrastive head (anisotropy margin 0.0006 -> recall@1 0.40->0.97) and single-leaf context (removes chat200m's multi-fact-selection weakness).
- Honest boundaries (measured / structural): (1) the 25% grounded miss is byte-copy error on long novel strings (garbled invented names) - the exact weakness the 800M core (`chat800m`, training) should reduce. (2) Retrieval is flat numpy over 1e5 keys; a true 1e12 store needs IVF-PQ + learned drill-down (unbuilt) - this validates retrieval QUALITY and scale-stability to 1e5, not the trillion-scale index engineering. (3) Queries are invented-fact schemas (held-out entities); open-domain query quality is untested. (4) Single seed, one model.
- Run: head `models/memory_milestone/d1e5/head.pt`; store `models/memory_milestone/d1e5/`; code `experiments/v2/memory/{store,reader,make_facts,train_head,eval_head_e2e,eval_memory}.py`.

## 2026-07-02: measured training throughput ceiling on M3 Ultra

- Measured: 0.5B transformer, bf16, MPS: ~4,858 tok/s eager, ~6,484 tok/s with torch.compile at fixed shapes (bs32/seq512). 1.5B: ~1,947 eager / ~2,187 compiled. MLX is the same tier as torch-MPS (not a lever). GPU is FLOP-bound at ~70 percent of realizable bf16 compute.
- Implication: wall-clock for any plan computes directly from these numbers; framework changes buy nothing, torch.compile buys ~35 percent, fixed shapes are mandatory (see failures 2026-07-03).
