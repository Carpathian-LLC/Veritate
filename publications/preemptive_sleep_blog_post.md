# The model learns while you type

*Sam Malkasian, Carpathian LLC — 2026-08-23*

We have a machine in the corner that exists to be humiliated. It is an Intel i7-9700T: eight cores, no hyperthreading, and a BIOS that locks it to 800 MHz — 40% of the clock it was sold with. Nothing about it is fast. That is the point. If a feature works there, it works on whatever is under your desk.

The feature we wanted was simple to say and annoying to build: **the model should learn from its conversations without anyone noticing.**

## The obvious version doesn't work

Our models improve by consolidating their own recorded exchanges into their weights — a short, low learning-rate training run over the conversations they actually had. On a Mac Studio this is pleasant. You talk to the model, it goes away for a while, it comes back slightly better at the things you talk about.

On the 800 MHz box it was a disaster. Training took seven of the eight cores, and asking the model a question meant waiting **three seconds for the first character**, then reading at less than half normal speed. The box wasn't broken. It was doing exactly what we told it to, and what we told it to do was fight itself for the only resource it had.

The standard fixes are all half-measures. Renice the trainer, and it still streams weights through the same memory bus. Cap its threads, and you have merely chosen a smaller fight. Wait for the machine to be idle, and on a single-user computer you are waiting for a moment that mostly doesn't come — which means the model mostly doesn't improve.

## The version that does

The fix turned out to be one that operating systems have supported since the 1970s: **stop the training process entirely while a person is waiting, and start it again afterward.**

Every time the model begins generating a reply, the trainer gets a `SIGSTOP`. When the box has been quiet for five seconds, it gets a `SIGCONT`. That is the whole mechanism.

| | first character | reading speed |
|---|---|---|
| nothing else running | 13 ms | 18.3 ms/byte |
| training, unyielding | 2,856–3,113 ms | 44.6–57.7 ms/byte |
| training, yielding | 12–23 ms | 17.9–18.2 ms/byte |

Talking to a model that is training is now indistinguishable from talking to one that isn't.

The reason `SIGSTOP` is the right tool, rather than something gentler, is that **a stopped process loses nothing**. It keeps its memory, its optimizer state, its exact position in the training step. Interrupt it fifty times and it still costs precisely the CPU time it would have cost uninterrupted — only the wall clock stretches.

That has a consequence we didn't expect. The intuition on slow hardware is to make each training step small, so an interruption wastes less work. But if interruptions waste *nothing*, that reasoning evaporates, and it inverts: you want the **largest** step that fits in memory, because the expensive part of a step is a fixed cost paid once per step regardless of how much data goes through it. Preemption didn't just make background training tolerable. It changed what the right training shape is.

## A bug that measured as working

Worth recording, because it is the kind that passes every test you think to run.

The controller decided how long to wait before its next check *before* going to sleep. So if a request arrived just after that decision, the trainer got stopped — and then stayed stopped until the next check came around, up to a full minute later. On a machine getting a message every thirty seconds, the trainer would have been suspended essentially forever.

Every latency measurement would have looked perfect. Serving was fast. The trainer was "running." It was simply never *executing*. We caught it by sampling the process state directly during a request instead of trusting the latency numbers, which is the sort of thing worth doing on any result that seems too clean.

## What we found while looking

Chasing where the milliseconds went turned up something more interesting than the thing we were measuring.

Decode on this architecture is not uniform. The model file carries a small table marking certain bytes — spaces, punctuation — as boundaries. When the model reads one of those, the next step runs an extra recurrent stack that other steps skip. In plain terms: **the first letter of every word costs five times as much as the letters inside it.**

You can see it in the data without any analysis. Sort the generated bytes by cost, and the cheap ones read:

> `here re any ifferent ays o earn istory.`

and the expensive ones:

> `a m d w t l h O w i t s h t a s p`

The sentence was "There are many different ways to learn history. One way is to study history through a scholarly perspective." Nineteen percent of the bytes — the word-initial ones — were consuming **54% of the total generation time**.

This also killed an optimization we were about to do. Seeing 18 ms/byte end-to-end against a 10 ms/byte forward pass, the natural suspicion is overhead: the Python, the JSON, the per-byte streaming. We measured it directly: the entire serving stack costs **0.02 ms/byte — two milliseconds out of 2,198, one tenth of one percent.** There was no overhead to remove. The gap was those word-initial bytes, and the way to attack them is quantization, since they are bound by memory bandwidth rather than arithmetic. Switching the same weights from 16-bit to 8-bit made generation **1.46× faster, with identical text across the compared greedy reply.**

One more, in the same vein. The engine sizes its own thread pool by testing 1, 2, 4, 8 workers and stopping when the next rung stops helping "enough." On this box 8 workers were 10.4% faster than 4 — just under the threshold, so it picked 4. The visible symptom was a machine that never used more than half its cores while generating, which looks exactly like a hardware limit and is not one.

## Why we think this matters

Continual learning is usually framed as a scheduling problem: find the idle window, take the hardware, give it back. That framing quietly assumes the window exists. On the hardware most people own, it doesn't.

Preemption replaces the scheduling problem with a priority problem, and the priority problem has a much better answer. The model doesn't need an idle machine. It needs to be interruptible in milliseconds and to lose nothing when interrupted — and the operating system gives you both for free. Consolidation can then run *continuously*: in the gaps between keystrokes, while you read a reply, overnight. It stops waiting for permission.

The honest limits: this is one CPU box at a locked clock, one model family, and it measures latency, not learning. It shows that background training can be made free to the person using the machine. It does not show the training is good — that is a separate result, on a separate page. And a preempted run on a busy machine still takes far longer in wall-clock terms than the same run on an idle one. The CPU time is conserved, not conjured.

But the machine in the corner now trains itself while someone talks to it, and the person talking cannot tell.
